# Lean hunt — what was actually broken, 2026-09-13

Authorship: the theorems are the repository author's. This file records only the proof
engineering: which declarations Lean was rejecting, why, what was changed, and the run id
that accepted the result. Nothing was compiled locally (the Lean release host and the
Mathlib cache are blocked from this container); every verdict below is a CI run.

Four defects were doing all of the damage, and a fifth was in the ledger rather than in any

## Defect 1 — recovered math batch D, one induction

`RecoveredMathBatchD.stepwise_strict_decrease_below_initial`

The proof did `intro n hn` and then inducted on `n` while `hn : 0 < n` was still in context.
Lean reverts hypotheses that depend on the induction variable, so the induction hypothesis
arrived as `0 < n + 1 → V (n + 1) < V 0` rather than `V (n + 1) < V 0`, and `lt_trans hs ih`
was an application type mismatch. Lean recovered with `sorryAx`, the axiom audit rejected it,
and that single proof made the whole certification job red — which is why **all 38**
declarations of batches A, B, C and D were failing. Batches A, B and C had been compiling
with clean axioms the entire time.

Repair: prove `∀ n, V (n + 1) < V 0` first, with nothing in context depending on the
induction variable, then derive the positive-index form by cases.

Accepted: `Title certification kernels` run **34758240472**.

## Defect 2 — Yang–Mills projector dynamics, two faults in one module

`ProjectorDynamics.lean`, which blocked `lake build` and therefore all seven modules.

**2a. `projectorCrossEnergy_eq_two_mul_couplingEnergy` carried `sorryAx`.**
The proof applied `rw [Finset.sum_comm]` to the whole goal. That rewrites the *first* double
sum it meets, which is the upper cross block, when the block that needs exchanging is the
lower one. The two sides were then summed in different orders and `ring_nf`, which treats a
`Finset.sum` as an atom, could not identify them. Repair: evaluate each oriented cross block
separately and exchange only the lower one. `half_projectorCrossEnergy_eq_couplingEnergy`
had inherited the same `sorryAx`.

**2b. `hasDerivAt_retained_transport_commutator` and the bridge theorem failed to elaborate.**
Two causes in one statement. The lambda binder in `fun t => (U t * retainedProjection * V t) i j`
was unannotated, so the derivative point `0` was defaulted to the naturals and Lean asked for
`NontriviallyNormedField ℕ`. And `retainedProjection` left its index types as metavariables,
so `K * retainedProjection` was not recognised as a matrix product ("Function expected").
Repair: annotate the binders `fun t : ℝ` and ascribe the projector's type.

Accepted: diagnostic run **34759183630** (all seven modules exit 0, `OVERALL=0`, every
declaration depending only on `propext`, `Classical.choice`, `Quot.sound`), then the official
gate `Yang Mills cross theorem closing steps` run **34759534925**, which additionally checks
declaration counts per module, runs `leanchecker`, and rejects `sorryAx` and `ofReduceBool`.

The other three new modules needed no repair. They were already compiling clean and the
earlier red runs said nothing about them:

| module | theorems | axioms |
|---|---:|---|
| ProjectorKernel | 3 | propext, Classical.choice, Quot.sound |
| CouplingFeedback | 4 | propext, Classical.choice, Quot.sound |
| ObservabilityKernel | 3 | `dual_certificate` and `presentation_invariant` need only propext and Quot.sound |

That covers `forcing_iff_kernel_not_le`, `dual_certificate`, `presentation_invariant`,
`redistribution_eq_zero_iff`, `memoryAtZero_eq_zero_iff`, `feedbackWith_factorized` and
`feedbackWith_eq_zero_iff_of_factor_right_inverse`.

## Why the failures were invisible

The cross-theorem workflow writes the compiler output only into an upload artifact, and
artifact blob storage is blocked by this environment's egress policy. The run log showed an
exit code and nothing else. A temporary job that compiled each module separately and printed
every diagnostic into the run log itself is what made the two defects readable. That job has
been removed now that the official gate passes.

## Defect 3 — Collatz finite-word barrier, an induction that forgot its argument

`OperatorFirst.collatzQWord_affine`, on `formalize/collatz-finite-word-barrier`.

The word acts on a rational by folding one affine step per letter, so the induction step has
to apply the hypothesis at a *different* rational than the one in the goal: the cons case
needs it at `collatzQStep a x`, not at `x`. The proof ran a plain `induction w`, which fixes
`x` for the whole induction, so `rw [ih]` reported that it could not find `collatzQWord w x`
in a goal reading `collatzQWord w (collatzQStep a x)`. Lean recovered with `sorryAx`, the
module failed to build, and all **five** Collatz declarations went red with it — including
`collatzWordMul_two`, `collatzBarrier_two` and `collatzQWord_two_lt_self`, whose own proofs
were clean the whole time.

Repair: `induction w generalizing x`, one word added. Nothing else in the file changes.

The statements are untouched, so the barrier result stands as the author wrote it: a
prescribed valuation word acts affinely, and when its multiplier is under one it pushes `x`
down exactly when `x` is above `collatzWordAdd w / (1 - collatzWordMul w)`.

Verified: `Lean hunt verification` run **34760273683**, job `collatz-finite-word-barrier`.
All five declarations report `[propext, Classical.choice, Quot.sound]`; no `sorryAx`.

## Defect 4 — ACC complete frontier, a build order, not a proof

`ACCFrontier.lean`, on `formal/acc-complete-frontier-2026-09-13`. **The mathematics was never
wrong and was never even reached.**

`acc-length-well.yml` compiled `ACCWell.lean` with `lake env lean`, which type-checks a file
but writes no `.olean`. The next step compiled `ACCFrontier.lean`, whose first line is
`import ACCWell`, and Lean failed at line 1 column 0 with `unknown module prefix 'ACCWell'`.
Four declarations were marked failing on the strength of an import that was never built.

Repair: emit the olean into the search path, `lake env lean ACCWell.lean -o
.lake/build/lib/lean/ACCWell.olean`, before compiling the frontier module.

Verified: `Lean hunt verification` run **34760273683**, job `acc-complete-frontier`. Both
frontier theorems report `[propext, Classical.choice, Quot.sound]`, and the four `ACCWell`
declarations behind them report `[propext]` and `[propext, Quot.sound]`.

Worth recording: `final_outside_forces_crossing` does its list induction as
`induction ms generalizing start` — the exact discipline whose absence broke the Collatz
proof. The frontier file is also careful in the way its docstring claims, refusing to turn
"the exit edge rises above the cap" into "the exit edge rises by exactly one" without a
bounded-jump hypothesis.

## Defect 5 — the ledger was wrong about twelve declarations

Not a proof fault at all. The ledger builder read `lean_lib` names out of `lakefile.toml` but
ignored the `roots` list a `lean_lib` may declare. On
`formalize/projector-conjugation-derivative` the library declares four roots, so `lake build`
compiles `TwoRailGeometry`, `TwoRailBridge` and `ProjectorConjugationDerivative` alongside
`OperatorFirst`. The builder saw one root, could not tie `ci.yml` to the other three files,
and reported twelve declarations as never compiled.

They had been compiling green since run **34717400111** on head `c06021a2f119`, every one of
them reporting an allowlisted axiom set, and two of them —
`figureEightCompatible_all` and `torus_implies_figureEight` — depending on no axioms at all.

Repair: parse `roots` as well as `name`. Exactly twelve rows change status; no other row
moves. The builder scripts now live in `ledger/tools/` so the counts can be reproduced rather
than trusted.

## Defect 6 — Warmup.lean did not compile at all

`Warmup.lean` was the last file with genuinely no coverage. It is not a lake root on any
branch, so `lake build` never touched it, and unlike `OperatorFirst.lean` it carried no
`#print axioms` lines. Its four theorems were given dependency reports in the file's own
established style and a job that compiles them — and the very first run of that job found
that **the file does not parse**:

```
Warmup.lean:64:58: error: unexpected token 'ᵀ'; expected ')'
Warmup.lean:70:48: error: unexpected token 'ᵀ'; expected ')'
Warmup.lean:84:14: error: Unknown constant `OperatorFirst.transpose_mul_of_symm`
Warmup.lean:85:14: error: Unknown constant `OperatorFirst.reciprocity`
```

The postfix transpose is notation scoped to the `Matrix` namespace, and the file never opened
it. The two reciprocity theorems therefore never elaborated, which is why the dependency
reports for them then asked about constants that did not exist. The two commutator theorems
above them are plain ring statements and had been fine.

Repair: `open Matrix` at file scope, exactly as `OperatorFirst.lean` does at its line 17. The
statements and proofs are untouched, and `OperatorFirst.lean` states the same four results and
has been compiling them green all along — so the mathematics was never in question, only this
copy of it.

This one is the argument for the whole exercise. A file sat broken while every branch holding
it stayed green, because nothing compiled it. Adding the job was what found it.

## A gap that is not a failure

On the branches that use `lean-action`, `axiom-audit` runs with `leanchecker-args:
OperatorFirst`, so it audits 22 declarations under that one root and no others. The remaining
roots still print a dependency report for every declaration, and those reports are clean, but
they are compiler output rather than an enforced gate. Listing every root in
`leanchecker-args` would turn them into one.
